## 2. 실패 경로 전수

불러오기 = 호스트 `gh_do_load` → `PC98_SaveState_FromFile` → `ApplyImage`. 실패 문구는 로그에 `LOAD … <- FAIL <사유>` 로 남는다.

| # | 위치 | 조건 | 화면 문구 |
|---|---|---|---|

### 2-3. 목록 표시 쪽 (실패 원인 3)

`PC98_SaveState_ReadThumb` 는 매직과 형식 버전만 확인한다 (빌드 ID·디스크·CRC 검사 안 함, 코드에 「목록 표시용」 주석). 따라서 **다른 빌드에서 만든 저장도 슬롯 목록에 사진·시각과 함께 「사용 중」으로 나오고, 「이어하기」 메뉴도 활성화된다.** 눌러야 비로소 실패한다.

### 5-2. 원인 2 를 재현하지 못한 이유와 대신 확인한 것

R1 이 전부 성공한 이유: 윈도우는 같은 컴퓨터를 켠 동안 같은 exe 를 거의 같은 주소에 올린다. 저장한 실행과 불러오는 실행의 주소가 같으면 저장된 포인터가 우연히 맞는다. 크래시가 난 doukyuusei2 는 저장(10-31 20:57)과 불러오기(그 후 재부팅 이후)의 주소가 달랐다고 보는 것이 맞다.

대신 슬롯 파일을 직접 분석했다 [파일: doukyuusei2/slot01.g98s, 해석 도구 perl, 읽기 전용]:
- `pc98_fm` 컴포넌트(343,396 B) 안에 **프로세스 주소 대역(0x00007FF6…) 값 656개**: `0x7FF65F…` 대역 600개, `0x7FF663…` 대역 56개.
- 크래시 로그의 쓰기 실패 주소 `0x00007FF6639ADC30` 은 **`0x7FF663…` 대역 안**이다. 즉 파일에 저장된 옛 주소로 쓰다가 죽은 것으로 맞아떨어진다.
- 크래시한 실행의 코드 주소는 `0x00007FF76B87…` 대역이라 저장했던 실행(`0x7FF65F…/0x7FF663…`)과 다른 주소에 올라와 있었다.
- 소스 주석에도 「opnch holds 24x12 table ptrs … raw here, fixed by restore_ptrs on load」 로 적혀 있다 — 포인터를 알고 통째 저장하고, 복원 후 `pc98_fm_restore_ptrs()` 로 고치는 설계. 그런데 그 고치는 함수가 `opngen_setreg` 를 부르고, `opngen_setreg` 안에서 `MIXER_FillUp` 이 돌 수 있다(스택에 그대로 찍힘). 믹서에 쌓인 시간이 있으면 틀린 포인터 상태로 소리 계산이 돌아 크래시한다 → **발생이 가끔**인 이유.
- 다른 컴포넌트: CPU·Mixer·Pic 은 대역 값 0개. Dos 9개는 포인터일 수도 있어 별도 확인 필요 [가설].
